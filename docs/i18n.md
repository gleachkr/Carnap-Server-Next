# Internationalization

Carnap's interface is translated with [Lingui](https://lingui.dev) in **no-macro
mode**: `i18n.t("…")` calls, PO catalogs under `src/locales/`, and native ICU
MessageFormat. Two properties shape everything below.

**A message's id is its English source text.** So a string with no translation
renders as clean English rather than as a dotted key, and a translator opening
the PO sees the sentence they are translating as the `msgid`. There is no
key-naming scheme to learn and no way for a typo'd key to reach a reader.

**Adding a language is almost a content task.** The code side is four
declarations across three files and no logic at all: nothing dispatches on
locale, nothing branches on language. See [Adding a locale](#adding-a-locale) for
the exact list — it is not the "one line" this document used to claim.

In scope: page chrome, student- and instructor-facing text, exercise widgets,
emails, flash notices, and author-facing compiler diagnostics. Out of scope, and
deliberately: RTL layout, the ~185 `AppHttpError` messages the JSON API carries
(the seam exists — see [The `AppHttpError` seam](#the-apphttperror-seam) — the
sweep does not), the WASM proof engine's own diagnostics (`@aufbau/compiler`
exposes no locale option, so its prose reaches the student's gutter in English
whatever we do; only our wrappers around it are translated — see
`src/worker/exercises/proof-engine-strings.ts`), and authored lesson content (a
separate project with a data-model cost).

## Commands

```bash
bun run i18n            # extract --clean + compile catalogs (the usual one)
bun run i18n:check      # are the committed catalogs what the source extracts to?
bun run i18n:coverage   # completeness report: which locales are incomplete
bun run i18n:report     # pseudolocale residue, ratcheted against a baseline
bun run i18n:baseline   # regenerate tests/i18n/pseudo-baseline.json
bun run i18n:overflow   # real Chromium, en-XA, looks for clipped layout
```

Extraction runs with `--clean`, so an id no call site passes any more leaves the
catalogs entirely. That is not tidiness: an obsolete entry is still *compiled and
shipped*, and one carrying the [ICU apostrophe](#the-icu-apostrophe) bug
(`'{token}'`, whose argument compiles away) will sit in the catalog forever
tripping the placeholder-survival sweep over prose nothing renders.

**There is no CI in this repo** — no workflows, no hooks. Every command here is
run by hand.

`i18n:check` and `i18n:coverage` both ask a read-only question, and both go
through `scripts/i18n-check.ts`, which extracts and compiles into a **temp
directory** seeded with the committed `.po` files and compares the result. So
neither writes to `src/locales/`, and both are meaningful on a dirty tree: the
check answers "are the committed catalogs what the source extracts to?" whatever
else is uncommitted around them. Seeding is not an optimization — extraction
merges into the catalog it finds (an empty directory reports every translation as
newly missing), and the PO header's `POT-Creation-Date` is carried over from the
file being replaced rather than stamped fresh.

`CARNAP_I18N_CATALOG_DIR` (read in `lingui.config.ts`) is what redirects the
output. Only the output moves: `rootDir` stays the repo, so the extraction scope
and the `#:` origin comments are byte-identical to a real `bun run i18n`.

The staleness question is therefore a `bun test` gate as well —
`tests/i18n-staleness.test.ts` calls the same `checkStaleness()` — so
`bun run validate` covers it without the script joining the command chain. Run
the command when the test fails: the test names the stale file, the script names
the messages that moved. `validate` also runs `build:client` first, so the
bundle-scan half of `tests/i18n-bundle-guard.test.ts` always has an artifact to
inspect.

`src/locales/*/messages.po` **and** the generated `messages.ts` are both
committed: `bun test` and `bun run check` run with no build step, and the Worker
imports the compiled catalogs as source.

### How `i18n:overflow` reaches the pseudolocale

`bun run i18n:overflow` passes `--lang=en-XA`, which becomes an
`Accept-Language` header, because `?lang=` is deliberately not a detection
source. A *stored* account preference normally outranks `Accept-Language` — and
the audit signs in as staff to reach the instructor routes, so it hits exactly
the case where a stored preference exists. That is why the pseudolocale is the
one language that outranks a stored preference (see
[Locale resolution](#locale-resolution)): without the exception this check asked
for `en-XA`, silently measured the account's own language, and reported a clean
run over a page it never rendered in `en-XA`. Every overflow run before
2026-07-27 measured German that way.

The script also compares the landed `<html lang>` with `--lang`. A mismatch under
`--lang=en-XA` means the precedence rule regressed, so it **fails the run** even
in `--report` mode; a mismatch under any real language is audit-account hygiene
(clear the stored preference, or pass `--email=ADDR` for an account that has
never chosen a language) and only warns.

## The one naming rule

> Whatever holds a translator must be **named `i18n`**.

The extractor matches calls by the *receiver's name* — `i18n.t(...)`,
`i18n._(...)`, or any member expression ending in `.i18n` — and never looks at
imports. Consequences:

```ts
i18n.t("Courses");                    // extracted
context.i18n.t("Courses");            // extracted
const { t } = i18n; t("Courses");     // extracted: NOTHING, silently
const translate = i18n; translate.t("Courses");  // likewise nothing
context.get("i18n").t("Courses");     // likewise nothing
```

**The last line is the one that actually bit**, and it deserves its own
sentence: a *call expression* in receiver position is not a name, so the
extractor does not see it, however plainly it spells `i18n`. 33 call sites were
written that way and 26 ids had never entered the catalog at all — mostly page
titles on error paths, so a German instructor who failed validation got a German
validation message under an English heading. Nothing complains: an id that never
reaches the catalog has no translation to be missing, and because ids are the
English source text the page keeps rendering perfect English in every language.

Hoist first, always:

```ts
const i18n = context.get("i18n");   // then i18n.t(...)
```

`tests/i18n-extraction.test.ts` is the detector. It asserts every string literal
passed to a `.t(...)` call under `src/` is a key in the English catalog, which
covers this case, a receiver named anything else, a destructured `t`, and a
literal edited at the call site but never re-extracted.

The extractor also reads **string literals only**. A message hoisted to a `const`
and passed in is dropped without a word, and a template literal is unreadable to
it (`i18n-extraction.test.ts` fails on those too):

```ts
const LABEL = "Courses";
i18n.t(LABEL);            // not extracted
i18n.t(`${n} courses`);   // not extracted; use "{count} courses" + values
```

The receiver rule is also what lets code that never sees the real translator —
shared widget and diagnostic modules taking an `i18n: Translator` parameter — be
extracted exactly like the Worker's own calls.

## Where the translator comes from

| You are writing | You get `i18n` by |
|---|---|
| A JSX view component | `useI18n()` — re-exported from `./layout`, defined in `./i18n-context` |
| A route handler | `const i18n = context.get("i18n");` — hoisted, never inline |
| A service, or anything a browser bundle can reach | an `i18n: Translator` parameter |
| A service that has no translator to take | `deferred.i18n.t(…)` — see below |

### When there is no translator: `deferred`

Some messages are written where no locale is knowable — an `AppHttpError` thrown
four layers below the request, a compiler diagnostic produced in code that also
runs in the browser. They cannot call `i18n.t`, and writing the
`TranslatableMessage` by hand (`{ message: "…" }`) puts the text nowhere the
extractor looks, which means it is English forever with nothing failing.

`src/worker/i18n/deferred.ts` is the shape for that case:

```ts
throw badRequest(
  "invalid_course_title",
  deferred.i18n.t("Course title must be between 1 and 200 characters."),
);
```

`deferred.i18n` translates nothing — `t` hands its arguments back as a
`TranslatableMessage`. It is *named* `i18n` because that is the only thing the
extractor matches on, and it is reached through `deferred.` so it never collides
with the request-scoped `i18n` a route file already holds. `AppHttpError` resolves
the English itself, so `Error.message`, the JSON envelope, and the logs are
indifferent; `error.localize(i18n)` is what words it for a reader.

Two limits. `resolveMessage` does `{name}` substitution, **not** ICU — a deferred
message cannot ask for plural or select agreement with one of its values, so decide
the wording at the call site instead. And never interpolate English prose into one:
`` `${action} is only available for graded assignments.` `` reaches the catalog as
a loose noun phrase with English word order baked in. Push the whole sentence to
the caller. A *field label* nested as a `TranslatableMessage` param is the accepted
exception, because "{label} is required." translates cleanly.

`tests/error-messages.test.ts` enforces this across `src/worker/application/`: no
error message there may be a bare string literal. `src/worker/routes/` is
deliberately exempt — its literals are JSON-shape validators ("User ID must be a
string.") that answer a malformed API request and cannot be provoked through a
form, so translating them would only ask volunteers to render prose no reader
meets.

`useI18n()` lives in its own module rather than in the layout because the
standalone content document needs the same provider and is compiled into the
browser preview bundle: importing the layout there would drag the app shell and
its styles into that bundle. Import from `./layout` in ordinary pages, from
`./i18n-context` in anything the preview reaches.

It **throws** when no provider is in scope rather than falling back to English. A
silent fallback would render fine in English and quietly ship untranslatable
text, which is precisely what the pseudolocale gate exists to catch. The provider
is safe under concurrency only because the render is synchronous — without
`nodejs_compat` there is no `AsyncLocalStorage`, so `hono/jsx` keeps provided
values in a module-scoped store for the duration of `toString()`. The
`typeof rendered !== "string"` guards in `renderShell` and `contentDocumentHtml`
are what hold that precondition: an async view component would break it, and they
turn that into a loud error instead of a wrong page.

`Translator` (`src/worker/i18n/translator.ts`) is a tiny interface — `t()` plus a
readonly `locale` — defined without importing anything. `@lingui/core`'s `I18n`
satisfies it structurally, so nothing wraps it: a wrapper would break extraction
and buy nothing.

`locale` **rides on the translator** rather than travelling beside it. A tag
passed as a second argument is a tag that can disagree with the prose, and it
did: the pair used to be read from two context keys at every call site, and each
site had to remember to keep them in step. Anything needing the tag as well as
the words — `<html lang>`, `Intl` formatting inside a client script, the
preview's rebuilt document — takes both off one object. Two call sites still pass
an `i18n` and a `locale` side by side (the email sender is one); they are noted
where they are, and they are the shape to remove, not to copy.

**Never import `src/worker/i18n/index.ts` from code a browser bundle reaches.**
`src/client/editor-preview.ts` imports the Worker's markdown compiler, content
renderer, and content-document builder, so those modules and everything they
reach are compiled into a browser bundle. One import of `i18nFor` there ships
`@lingui/core` and every catalog to the browser.
`tests/i18n-bundle-guard.test.ts` is the backstop; the rule is the fix.

Where a leaf needs the *set* of locales rather than their contents — validating a
stored preference, matching an LTI claim — import `src/worker/i18n/locales.ts`,
which reaches no catalog.

## Locale resolution

Precedence: **`Accept-Language: en-XA` > `users.locale` > `carnap_locale` cookie >
`Accept-Language` > `en`**.

The pseudolocale at the top is the one exception, and it is there so
[`i18n:overflow`](#how-i18noverflow-reaches-the-pseudolocale) can measure what it
claims to. It is safe because nobody asking for `en-XA` can be expressing a
choice: it stays out of `SELECTABLE_LOCALES`, so a profile save refuses it and no
row can hold it, and no browser sends it unbidden. Keep it that way —
the moment the pseudolocale becomes selectable, this exception starts overriding
real readers' preferences.

Two middleware passes, because the stored preference is only knowable after auth
resolves the actor, while a request rejected *during* auth still needs a language
to render its error page in (`src/worker/app.ts`):

```
requestIdMiddleware()
localeDetectorMiddleware()   // cookie → Accept-Language → en, then applyLocale
actorMiddleware()
localeMiddleware()           // applyLocale again; users.locale can now win
csrfMiddleware()
```

Both passes go through the same `applyLocale(context, requested)`
(`src/worker/middleware/locale.ts`), which owns the precedence rule and sets
`language` **and** `i18n` together. Two things follow.

`AppVariables.i18n` is typed as always present, and phase one is what makes that
true rather than a lie for everything before `localeMiddleware` — the actor
lookup, CSRF, and `app.onError`, which is to say precisely the code that runs
when a request is being rejected and most needs words for it. Phase two only
ever *upgrades* the pair.

And any route that resolves a locale mid-request — an LTI launch adopting the
platform's — calls `applyLocale` rather than setting the keys itself, so it
cannot promote itself above a stored preference and cannot leave the tag and the
translator describing different languages.

The detector reads **cookie and header only** — not `querystring` (a `?lang=`
link would let anything that can put a URL in front of someone repin their
language, and LTI launches carry platform-controlled parameters) and not `path`
(`lookupFromPathIndex: 0` would read the leading `courses` of every URL as a
language tag). Its own cookie writer is off (`caches: false`): it fires on a
*sniffed* `Accept-Language` match, which would pin a guess as if it were a
choice. `src/worker/cookies.ts` owns cookie writes.

**Choosing a language** is a field on the profile form — a `<select name="locale">`
saved by `POST /profile` along with the name (`src/worker/web/profile.tsx`, routed
in `src/worker/routes/web.ts`). There is no switcher anywhere else: a signed-out
reader gets the language their browser asks for, because a `<select>` in the
footer of the login page put a prominent question to someone who has already
answered it in `Accept-Language`, before they have any reason to care what the
site's chrome is called. Anyone who wants a different language than their browser
asks for can say so once they have an account to store it on.

The empty option — "Match my browser" — stores `null` and *clears* the cookie
(`clearLocaleCookie`), because a cookie left behind would keep answering the
question the reader just withdrew: detection reads it before `Accept-Language`.
Choosing a language writes the cookie as well as the row, so logging out does not
silently revert the language, and so the choice survives on a shared browser. The
save needs no confirmation of its own: the page comes back written in the chosen
language.

**An LTI launch** reads `launch_presentation.locale` and adopts it *only when the
browser carries no locale cookie yet* — someone reading Carnap in English inside
a German Moodle chose that. It also calls `applyLocale`, because a Deep Linking
launch renders the picker in that same response; the cookie alone would arrive a
request too late.

The locale cookie is written by `src/worker/cookies.ts`, which owns every cookie
write in the app. It is `SameSite=None` **whenever it is `Secure`** — that is,
everywhere but plain-http local dev, where browsers reject `None` without
`Secure`. Unconditionally, not per call site, unlike the session cookie, which
keeps its `Lax`-unless-asked default.

The reason is the launch. A launch is a cross-site POST and a `Lax` cookie is not
sent on one, so the launch saw no cookie, concluded the reader had never chosen,
and overwrote a deliberate choice with the platform's language. The cookie is
`HttpOnly`, authorizes nothing and identifies nobody, and the worst a cross-site
request can do with it is render a page in the reader's own language — so `Lax`
was buying no defence to give up.

### Anything not rendered to the requester

The precedence rule above answers "what language is *this page*", and using it
for anything else is a bug with a very quiet symptom. **Email is composed for its
recipient, not for the browser that triggered it.**

The login email is the sharp case: the request that asks for a login link has no
actor *by definition*, so reading the requester's locale gave a user who chose
German on their account and then asked for a link from a fresh English browser an
English email — the exact case that justifies storing the preference on the user
row rather than leaving it in a cookie. `startNativeLogin` now looks the address
up and returns the recipient's stored locale, which the sender uses in place of
the request's. That lookup runs unconditionally and never reaches the response,
and `tests/i18n-routes.test.ts` pins the response as byte-identical (status,
headers, body) between a known and an unknown address, so the only asymmetry
stays in the mail itself.

The LTI account-link branch follows **recipient, then launch, then request**.

### The pseudolocale

`en-XA` is the generated pseudolocale. It is reachable with
`Accept-Language: en-XA` — which outranks a stored preference, see
[Locale resolution](#locale-resolution) — but stays off the profile form, hence
`SELECTABLE_LOCALES` alongside `SUPPORTED_LOCALES`.
`SELECTABLE_LOCALES` is **derived** (`SUPPORTED_LOCALES` minus `PSEUDO_LOCALE`),
not listed. It was the one locale list `tsc` did not force you to update, which
made it the one place adding a language failed *silently*: the new language would
resolve, translate, and serve via `Accept-Language`, and simply never appear on
the form.

## Adding a locale

Four edits across three files, plus the catalogs themselves. In this order:

1. **`lingui.config.ts`** — add the tag to `locales`. Without this, extraction
   never scaffolds a `.po` for it.
2. **`src/worker/i18n/locales.ts`** — add the tag to `SUPPORTED_LOCALES`. It is a
   `const` tuple, so `SupportedLocale` widens and `tsc` immediately demands the
   next two edits. Leave `SELECTABLE_LOCALES` alone: it is derived.
3. `bun run i18n` to scaffold `src/locales/<tag>/messages.po` and its compiled
   `messages.ts`. The module has to exist before the next step can import it.
4. **`src/worker/i18n/locales.ts`** — add an entry to `LOCALE_NAMES`, an
   **endonym**: the language named in itself, so a reader can find their own.
5. **`src/worker/i18n/index.ts`** — import the new catalog and add it to
   `CATALOGS`.
6. Translate; `bun run i18n:coverage` reports what is still missing. Re-run
   `bun run i18n`, and commit both the `.po` and the generated `.ts`.

Adding to `SUPPORTED_LOCALES` alone will not typecheck, and that is the design:
`LOCALE_NAMES` and `CATALOGS` are both `Record<SupportedLocale, …>`, so the
compiler names every remaining place a new language has to be accounted for. Only
`lingui.config.ts` is outside that net, and it fails loudly by producing no
catalog.

Nothing beyond those three files knows how many locales exist. No route, view, or
service branches on the tag.

## Writing a translatable message

### Whole sentences, never fragments

A sentence assembled from pieces bakes English word order in — a translator who
needs the date first cannot say so, and the fragments reach the catalog as loose
words. Pass the whole sentence and let the translator place the placeholder.

```tsx
// No.
<>{i18n.t("Opens")} <Time value={opensAt} /></>

// Yes.
const [before, after] = splitAtValue(
  i18n.t("Opens {when}", { when: VALUE }),
);
return <>{before}<Time value={opensAt} />{after}</>;
```

`VALUE` is a NUL sentinel and `splitAtValue` cuts the formatted message at it, so
an *element* can occupy a placeholder without the sentence being torn up. No
message and no translation of one can contain a NUL, so the split can never land
in the middle of real prose.

### `i18n.t` formats; it does not return a template

An ICU argument that was not supplied formats as the **empty string**. So a
message the *browser* will fill must be requested with its placeholders held
open:

```ts
// Wrong: comes back as "Correct cells:  of ".
i18n.t("Correct cells: {count} of {total}");

// Right.
i18n.t("Correct cells: {count} of {total}", placeholders("count", "total"));
```

`placeholders(...)` (in `translator.ts`) returns `{ count: "{count}", … }`, i.e.
it asks ICU to substitute each placeholder with itself.

### Two same-worded strings needing different translations

`msgctxt` **cannot** do this job here. With explicit ids the catalog is keyed by
id alone and the runtime looks up that flat key, so two `"Open"`s collapse into
one entry and one of the two renders the wrong word. Make the *id* unique and
supply the display text separately:

```ts
i18n.t("Open (assignment availability)", {}, {
  message: "Open",
  comment:
    "Disambiguating id; only the word Open is shown. " +
    "An assignment available now, with no closing date.",
});
```

Untranslated, that still renders the clean `"Open"`. Never reach for `context`.

The `comment` is not optional politeness. It reaches the PO as a `#.` line, and
without it the translator sees a `msgid` that is *not* the string being shown and
has no way to know the parenthetical is a disambiguator rather than text. Every
disambiguated id in the catalog carries one, and they say so in as many words —
see `src/locales/README.md`, which promises translators these exist.

### The ICU apostrophe

In ICU, `'` starts an escape **only** when followed by `{`, `}`, or (inside a
plural) `#`. So `':|-:'`, `'auto'`, `don't` are all fine; only a *quoted
placeholder* breaks:

```
"Expected '{token}'."   →  renders the literal text {token}
"Expected “{token}”."   →  correct; typographic quotes, and German gets „…“
```

Use typographic quotes around placeholders. It reads better and cannot misfire.

This is checked, and had to be: `i18n-catalogs.test.ts` reads the *compiled* ICU
AST rather than the string, so it sees the argument that the escape ate. Reading
the message text would not — `'{token}'` looks like a placeholder right up until
Lingui compiles it away.

### Plurals

Native ICU, so agreement is the translator's to state, and a language with
`few`/`many` can say so:

```ts
i18n.t("{count, plural, one {# attempt} other {# attempts}}", { count });
```

**Only on the server.** A count the *browser* computes has no plural selector
behind it: the client fills placeholders with `formatMessage`, which is plain
`{name}` substitution — no ICU, no `select`, no number or date formatting (see
`ExerciseHydration.strings`). So copy whose number the client supplies must be
phrased with the count as a **bare value** rather than inflecting a noun:

```ts
// Right: the browser only has to drop two numbers in.
"Correct cells: {count} of {total}"

// Wrong: no client-side code can choose between "cell" and "cells".
"{count, plural, one {# cell correct} other {# cells correct}}"
```

There is one ICU catalog and one runtime, and it is the Worker's.

## Text that reaches the browser

No i18n runtime ships. The server resolves strings for the viewer's locale and
pushes them through three channels:

- **Exercise widgets** — the per-exercise hydration payload's `strings` field
  (`src/worker/exercises/hydration.ts`), read client-side as
  `strings[id] ?? id`, so a missing entry degrades to English. **Review-mode
  widgets get a real payload too** (`reviewHydrationScript`, filled by the same
  `exerciseStrings` the answer path uses). A review is a rendered widget, not a
  picture of one — the Fitch review really does upgrade and mount a read-only
  editor — and it went without one for a while. Nothing looked broken because no
  review path calls `t()` yet; the first one to do so would have rendered English
  inside an otherwise translated page. `tests/exercise-review-hydration.test.ts`
  pins it because it cannot be observed.
- **Layout and page scripts** — a JSON payload alongside each inline script
  (`src/worker/web/ui-strings.ts`), read through `readStringsPrelude` and looked
  up as `S.key || "English"`, so a page cached from before a payload existed
  still says something. **Do not interpolate strings into script bodies**; the
  scripts stay static.
- **The authoring preview** — `EditorUiStrings.preview`, a flat catalog-id → text
  map plus the locale it was resolved for. The preview bundle rebuilds the whole
  content document on every keystroke through the same `contentDocumentHtml` and
  `exerciseStrings` the server render used, and hands them a `payloadTranslator`
  over that map. It used to hand them `passthroughTranslator`, so a German
  author's first keystroke turned every widget label English inside a document
  still declaring `lang="de"` — wrong prose *and* a WCAG 3.1.1 failure, and
  invisible to the pseudolocale gate, which only exercises the server render.
  `passthroughTranslator` is now a **test fixture**, not a production path;
  nothing in the Worker uses it.

The two open-ended maps in the editor payload — the diagnostics map and the
preview strings — go through `translatedStrings`, which **drops any entry whose
translation is the text the reader would have fallen back to anyway**. It
measures against `options.message ?? id` while the builder resolves, not over the
finished map, so a disambiguated id resolving to its own display text goes too
and the keys that survive are catalog *ids* rather than whatever the builder
keyed its own map by. In English that is all of them: the diagnostics map alone
was 9.2 KB of `{"X":"X"}` on every editor page, and English is now 397 bytes.

The fixed-shape payloads (`layoutUiStrings`, `exerciseUiStrings`,
`reviewUiStrings`, and the per-widget hydration `strings`) are not filtered —
they are small and their readers index them by a known key.

The `locale` travels *in* the editor payload rather than being read back off
`document.documentElement.lang`, so a rebuild cannot word itself in one language
while declaring another. That was the second half of the same bug: prose and
language declaration are two channels, and a rebuild that lost its prose kept the
tag.

A translated string is now **data in markup**, which it was not when it was an
English literal: a `</script>` or a `"` inside a translation will break whatever
it is pasted into. Payloads go through `jsonScriptContent`, and nothing in
`src/client` or `src/worker` uses `innerHTML` any more — spinners that built SVG
with `aria-label="${label}"` were a real instance of this, not a hypothetical.

Drift between what the server sends and what the client looks up is prevented by
a DOM-free shared strings module per widget: the builder's return type gives
`type XStringId = keyof ReturnType<typeof buildXStrings>`, the element imports
that *type* but never the builder, and `tsc` then rejects any `this.t()` argument
that is not a member.

`CarnapExerciseElement<StringId>` defaults `StringId` to **`never`**, not
`string`. A widget that forgets the parameter gets an empty `strings` payload, so
every lookup would fall back to English in every locale, silently and forever.
`never` makes `t()` uncallable until the subclass names its union — which is the
point at which the server side has to exist.

**Never branch on translated prose.** A count driven by
`label.textContent.trim() === "Needs review"` silently breaks the moment that
label is translated; use a `data-` attribute. This is the bug class localization
introduces, and it is worth grepping for before translating any label a script
reads.

## Compiler diagnostics

Author-facing diagnostics are the awkward case: produced in DOM-free code that
also runs in the browser preview, with text not fixed at the call site, and
sometimes nesting one message inside another. They travel as data —
`TranslatableMessage`, an unfilled English source text (which *is* the catalog id)
plus the values that fill it, one of which may itself be a `TranslatableMessage`.

```ts
diagnostic(line, "invalid_formula", "Could not parse formula “{formula}”: {detail}", {
  params: {
    // The parser's own complaint, nested rather than pasted in, so it gets
    // translated along with the sentence quoting it.
    detail: parsed.errors[0] ?? { message: "syntax error" },
    formula: trimmed,
  },
});
```

Three resolvers, one recursion (`translator.ts`):

| Resolver | Used by |
|---|---|
| `resolveMessage(message)` | JSON API, logs, tests — plain English |
| `translateMessage(message, i18n)` | the Worker, against a real catalog |
| `resolveMessage(message, stringsResolver(map))` | the browser, against a sent map |

Every sentence the compiler can emit is listed once in
`src/worker/application/content/diagnostic-strings.ts`, and
`CompilerDiagnostic.message` is typed as `keyof` that map. A recursive
template-literal type then extracts the `{slots}` from the id, so `params` is
**required exactly when the message has placeholders** and its keys must match
them. Adding a diagnostic without listing its sentence is a type error, not a
silently untranslated string.

### The `AppHttpError` seam

`AppHttpError` takes an optional `translatable` and offers `localize(i18n)`. An
error constructed without one renders `message` exactly as it always did, which
is why the ~185 existing validator messages needed no changes. HTML error paths
call `error.localize(context.get("i18n"))`; the JSON API keeps using
`error.message`.

`tests/i18n-pseudo.test.ts` is the **hard gate** — it asks a question with no
false positives, so it fails the suite. `bun run i18n:report` is its advisory
counterpart over the same fixtures, ratcheted rather than absolute, because
telling unwrapped prose from a course title, a logic formula, an id or a proper
noun needs an allowlist, and an allowlist maintained forever rots into noise.

The gate catches the commonest regression by far: a *second*, hard-coded copy of
a string that is wrapped elsewhere. Under the pseudolocale the wrapped copy is
mangled and the duplicate is not, so the survivor names itself. That mistake is
invisible both to `lingui extract` (which sees the wrapped call and is satisfied)
and to reading the diff (the duplicate is in a file nobody touched).

One caveat on its failure messages: a *phrase* can also be a substring of a
longer sentence that was never wrapped at all — `AppHttpError` messages are
English literals by design — in which case the gate reports something real under
a misleading explanation. A true positive with the wrong story, not a false one.

**Be honest about what it covers.** A message it can find is one that (a) passes
the searchability filter and (b) some fixture actually renders. Measured today:
698 catalog ids, 502 searchable, **305 observed across 61 fixtures — 43%.** It
was 10.8% until the fixture set was widened from 12 of 44 render functions to all
44; the gradebook, the LTI pages, the flash notices and the emails had *zero*
observable ids, and no error page had a fixture at all, which is exactly why a
batch of untranslated error-path titles survived the sweep and had to be found by
reading routes by hand. The filter was never the bottleneck. Fixtures are.

The searchability predicate is **≥12 characters *or* contains a space**, and no
`{`. Ids with ICU placeholders never appear verbatim anyway. The space clause is
measured, not guessed: of 150 short ids only 8 collide with anything across the
fixture set and every one is a single word ("Score" inside
`America/Scoresbysund`, "Prove" starting a seeded lesson), while **zero of the 28
multi-word short ids collide**. That admits `Add staff`, `Export CSV`, `Hide
grades` — the labels most likely to be typed out a second time by hand — for +21
observable ids and no false positives, and it needs no allowlist to maintain.

The bundle guard is **two layers**, because each alone has a hole. A module-graph
walk from the entry points named in `build:client` needs no build artifact, works
on a fresh clone, reports the offending import chain, and cannot be defeated by a
minifier — the import edge either exists or it does not. The bundle scan is the
second layer, for anything the walk's own resolver misses; it **fails** on an
unbuilt tree rather than skipping, because it used to skip, and `public/` is
gitignored, so on a fresh clone it checked nothing and passed. Do not grep for an
`@lingui` marker: the specifier is resolved away and `setupI18n` is renamed, both
measured at zero occurrences in a real minified build of a deliberate leak. The
scan's markers are `__lingui_octothorpe__` (an internal literal that does survive
minification) plus prose lifted from the compiled `de` catalog at run time, so a
translator rewording a message cannot silently disarm it.

Several of these tests exist because the corresponding mistake is **silent** —
the app keeps rendering flawless English while every other language quietly dies.
The sharpest is `setupI18n`'s `messages`, which is keyed *by locale*
(`{ de: catalog }`, not the catalog): a bare catalog is accepted and yields an
empty active one in which every message resolves to its own id. Hence one
construction site (`i18nFor`) and a test asserting a real translation comes back.

For the same reason, several of them assert a floor on how much they inspected:
`i18n-extraction` on the number of literals checked, `i18n-pseudo` on having ids
to search for and fixtures to search, the bundle guard on modules reached and
markers derived. A gate that quietly stops matching anything looks exactly like a
passing run.

## Deploying

**Outstanding — this is not configured yet.** `flake.nix` exports
`NODE_ENV=development`, so a `wrangler deploy` from the devshell bakes that in
and keeps Lingui's runtime message compiler alive, dragging the full ICU parser
into the deployed Worker instead of letting esbuild drop it.

Add to `wrangler.jsonc`:

```jsonc
"define": { "process.env.NODE_ENV": "\"production\"" }
```

and repeat it under **every named environment** you deploy: `define` is not
inherited by named environments, so a top-level block alone leaves
`wrangler deploy --env <name>` in development mode.

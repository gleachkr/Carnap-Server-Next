# Internationalization

The interface uses [Lingui](https://lingui.dev) without macros. Source code
calls `i18n.t("English text")`; PO catalogs and compiled TypeScript catalogs
live under `src/locales/`.

Message IDs are normally their English source text. A missing translation
therefore falls back to readable English. This also means missing extraction
can go unnoticed in an English session, so the repository tests both
extraction and rendered output.

Translated text includes pages, exercise controls, emails, notices,
application errors shown in HTML, and author-facing compiler diagnostics.
JSON errors and logs retain English messages. Authored lessons are not
translated, and RTL layout is not implemented. The proof engine manages its
own diagnostic translations separately.

## Commands

Enter `nix develop` before using project tools.

```sh
bun run i18n            # Extract with --clean, then compile
bun run i18n:check      # Check catalog staleness without changing files
bun run i18n:coverage   # Report missing translations
bun run i18n:report     # Report pseudolocale residue
bun run i18n:baseline   # Update the pseudolocale report baseline
bun run i18n:overflow   # Check expanded text in a running browser
```

After changing user-facing source text, run `bun run i18n` and include both
the `.po` and generated `messages.ts` files in the change. The Worker imports
the compiled catalogs directly. Extraction uses `--clean` to remove messages
no longer referenced by source code.

`i18n:check` extracts and compiles in a temporary directory seeded with the
current PO files, and fails when the committed catalogs are stale;
`i18n:coverage` compiles the same copy with `--strict` and extracts nothing
first — coverage is a property of the committed catalogs, not of the source.
Neither modifies `src/locales/`.
`CARNAP_I18N_CATALOG_DIR` redirects catalog output without changing the
extraction root or source-location comments.

`tests/i18n-staleness.test.ts` uses the same staleness checker, so
`bun run validate` covers catalog consistency without regenerating catalogs.
The standalone command gives more detail about which messages changed.
`validate` also builds browser bundles before testing them for accidental
catalog imports.

There is no CI or hook running these commands automatically.

## Name the translator `i18n`

The extractor recognizes the receiver's name, not its import or type. Use
`i18n.t(...)`, `i18n._(...)`, or a member expression ending in `.i18n`.

```ts
// Extracted:
i18n.t("Courses");
context.i18n.t("Courses");
deferred.i18n.t("Courses");

// Not extracted:
const { t } = i18n;
t("Courses");
const translate = i18n;
translate.t("Courses");
context.get("i18n").t("Courses");
```

In route handlers, assign the translator before calling it:

```ts
const i18n = context.get("i18n");
const title = i18n.t("Courses");
```

Pass string literals as IDs. Constants and template literals are not
extracted:

```ts
const LABEL = "Courses";
i18n.t(LABEL);                 // Not extracted

// Use a literal with values instead of an interpolated template.
i18n.t("{count} courses", { count });
```

`tests/i18n-extraction.test.ts` checks literal calls against the English
catalog and rejects unsupported call forms.

## Where the translator comes from

- **JSX views:** call `useI18n()`, exported by `web/layout.tsx` and defined in
  `web/i18n-context.tsx`.
- **Routes:** use `const i18n = context.get("i18n");`.
- **Services and shared code:** accept an `i18n: Translator` parameter when
  the caller can supply one.
- **Code with no locale:** create a deferred message for later translation.

`Translator` in `src/worker/i18n/translator.ts` contains `t()` and a read-only
`locale`. It imports no catalogs or runtime dependencies. Lingui's `I18n`
implements this interface structurally.

Read the locale from the translator instead of passing a second tag that
could disagree with it. This keeps formatted values, prose, and `<html lang>`
consistent.

### JSX context and synchronous rendering

`useI18n()` throws if no provider is present. It does not silently fall back
to English.

The Hono JSX context used here requires synchronous rendering. Guards in
`renderShell` and `contentDocumentHtml` reject non-string render results.
Do not introduce async view components without replacing this concurrency
assumption.

Code used by the editor preview must import the context from
`web/i18n-context.tsx`, not from the layout module. Importing the layout would
also include the application shell and its styles in the preview bundle.

### Keep catalogs out of browser bundles

Never import `src/worker/i18n/index.ts` from a module reachable by browser
code. It imports Lingui and all catalogs. The editor preview uses the shared
Markdown compiler, renderer, and content-document builder, so this applies
to those modules and their dependencies too.

For locale tags and validation only, import `i18n/locales.ts`. For an
interface type, import `Translator` from `i18n/translator.ts`.

`tests/i18n-bundle-guard.test.ts` checks both the client import graph and the
built bundles. The bundle check fails if the assets have not been built.

## Deferred messages and application errors

Use `deferred.i18n.t` when a message is created before a locale is known:

```ts
throw badRequest(
  "invalid_course_title",
  deferred.i18n.t("Course title must be between 1 and 200 characters."),
);
```

The helper in `src/worker/i18n/deferred.ts` returns a `TranslatableMessage`
containing an ID and values; it does not translate. Its receiver is named
`i18n` so Lingui extracts the literal. Do not construct a message object by
hand where extraction depends on this call.

`AppHttpError` and `LtiLaunchError` accept either a string or a deferred
message. They resolve `Error.message` to English for JSON responses and logs.
HTML paths call `error.localize(i18n)`.

`tests/error-messages.test.ts` rejects bare error-message literals in
`src/worker/application/`. Route-level JSON-shape validators are exempt;
those messages describe malformed API input rather than normal form errors.

Deferred resolution supports `{name}` substitution, not ICU plural or select
expressions. Choose an appropriate whole sentence at the call site. Do not
insert untranslated English fragments such as an action name into a generic
sentence. A translated field label nested in a message such as
`"{label} is required."` is supported.

## Locale resolution

Precedence is:

1. An explicit `Accept-Language` request for the `en-XA` pseudolocale.
2. The signed-in user's stored `locale`.
3. The `carnap_locale` cookie.
4. The normal `Accept-Language` match.
5. English (`en`).

The pseudolocale exception allows browser audits to override an audit
account's preference. `en-XA` is not selectable or accepted as a stored
profile preference. Keep it that way so the exception cannot override a real
user choice.

The application resolves locale twice:

```text
requestIdMiddleware()
localeDetectorMiddleware()
actorMiddleware()
localeMiddleware()
csrfMiddleware()
```

The first pass supplies a language for authentication failures. The second
can use the now-known account preference. Both call `applyLocale` in
`src/worker/middleware/locale.ts`, which sets `language` and `i18n` together.
A route that adopts a locale during a request, such as an LTI launch, must
use this helper too.

Detection reads the cookie and header, not URL query parameters or path
segments. Automatic cookie caching is disabled: a browser-language guess
must not become a stored choice. All cookie writes belong in
`src/worker/cookies.ts`.

### Choosing a language

The profile form saves a `locale` through `POST /profile`. Selecting a
language updates both the user record and cookie. The cookie preserves the
choice after logout.

**Match my browser** stores `null` and clears the locale cookie. Leaving an
old cookie would prevent the browser preference from taking effect.
There is no separate signed-out language selector.

### LTI launches

An LTI launch can adopt `launch_presentation.locale` when no locale cookie
exists. It also calls `applyLocale` immediately so a Deep Linking picker in
the launch response uses the correct language. A stored user preference still
has priority.

On HTTPS the locale cookie is `HttpOnly`, `Secure`, and `SameSite=None`.
Cross-site launch POSTs must carry it so the platform locale does not replace
an existing choice. On plain HTTP it cannot use `SameSite=None`, because
browsers require `Secure` with that setting. The cookie grants no authority.

### Email and other recipients

Choose a message's language for its recipient, not automatically for the
browser that requested it.

Native login requests have no authenticated actor. `startNativeLogin` looks
up the recipient's stored locale and supplies it for email delivery. The
lookup result is not exposed in the HTTP response. Route tests check that a
known and unknown address receive identical response status, headers, and
body.

LTI account-link email uses recipient preference, then launch locale, then
request locale.

### Pseudolocale and overflow

`en-XA` expands and alters English text to reveal untranslated strings and
layout assumptions. It belongs in `SUPPORTED_LOCALES` but not
`SELECTABLE_LOCALES`; the latter is derived by excluding `PSEUDO_LOCALE`.

`bun run i18n:overflow` sends `Accept-Language: en-XA` through the Chromium
accessibility harness. It also checks the resulting `<html lang>`. A mismatch
for the pseudolocale fails even in report mode. A mismatch for a real language
only warns, since an account preference may legitimately override the header.

See [Accessibility testing](./a11y.md) for the server and browser
requirements.

## Adding a locale

1. Add the tag to `locales` in `lingui.config.ts`.
2. Add it to `SUPPORTED_LOCALES` in `src/worker/i18n/locales.ts`.
3. Run `bun run i18n` to generate its PO and TypeScript catalog files.
4. Add an endonym to `LOCALE_NAMES` in `locales.ts`: the language's name in
   that language.
5. Import the generated catalog and add it to `CATALOGS` in
   `src/worker/i18n/index.ts`.
6. Translate the PO file, run `bun run i18n` again, and inspect
   `bun run i18n:coverage`.
7. Include both catalog files and run validation.

`LOCALE_NAMES` and `CATALOGS` are keyed by `SupportedLocale`, so typechecking
identifies missing entries. Do not edit `SELECTABLE_LOCALES` separately or
add locale-specific branches to routes and views.

## Writing messages

### Whole sentences, never fragments

Translators need control over word order. Pass a whole message, even when a
JSX element occupies part of it:

```tsx
const [before, after] = splitAtValue(
  i18n.t("Opens {when}", { when: VALUE }),
);
return <>{before}<Time value={opensAt} />{after}</>;
```

`VALUE` is a NUL sentinel. `splitAtValue` splits the formatted message around
it so the element can appear wherever the translation places the placeholder.
Do not concatenate a translated `"Opens"` with a date element.

### Preserve browser-filled placeholders

Lingui formats a message immediately. An unsupplied argument becomes an
empty string. For a template the browser will fill later, use `placeholders`:

```ts
i18n.t(
  "Correct cells: {count} of {total}",
  placeholders("count", "total"),
);
```

The helper supplies each placeholder as its own replacement text. Browser
code can then substitute the actual values.

### Disambiguate identical English text

With explicit IDs, `msgctxt` does not distinguish two messages with the same
ID. Use a unique ID and a separate display message:

```ts
i18n.t("Open (assignment availability)", {}, {
  message: "Open",
  comment:
    "Disambiguating id; only the word Open is shown. " +
    "An assignment available now, with no closing date.",
});
```

Always include a translator comment explaining the disambiguation. Otherwise
the PO file does not make clear that the parenthetical is not displayed.
The untranslated fallback uses `options.message`, so readers still see
`Open`.

### ICU apostrophes

An ASCII apostrophe before `{`, `}`, or a plural's `#` begins an ICU escape.
For example, `"Expected '{token}'."` prints the literal `{token}` instead of
substituting it. Use typographic quotes: `"Expected “{token}”."`.

Ordinary apostrophes in words such as `don't` are safe. Catalog tests inspect
the compiled ICU structure to detect placeholders lost through quoting.

### Plurals

Use ICU plurals for values known on the server:

```ts
i18n.t("{count, plural, one {# attempt} other {# attempts}}", { count });
```

Browser code has only plain `{name}` substitution, not ICU plural selection,
`select`, or number/date formatting. For a browser-computed count, use a
message such as `"Correct cells: {count} of {total}"`, not an ICU plural.

## Browser strings

The application's Lingui runtime and catalogs stay on the server. Translated
strings reach browser code through three payloads:

1. **Exercises:** `ExerciseHydration.strings`, populated by `ExerciseRegistry.strings`
   in both answer and review mode. Element lookup falls back to the English
   ID when a key is missing.
2. **Page scripts:** JSON next to static inline scripts, built in
   `src/worker/web/ui-strings.ts`. `readStringsPrelude` reads the payload;
   scripts retain English fallbacks for absent entries.
3. **Editor preview:** `EditorUiStrings.preview`, a map of catalog IDs to
   translated text plus the locale. `payloadTranslator` lets the shared
   renderer rebuild a translated document in the browser.

Do not use a passthrough translator in a production preview. A rebuild must
preserve both translated text and the matching language tag.

The editor's open-ended diagnostic and preview maps use `translatedStrings`
to omit entries equal to their fallback (`options.message ?? id`). Fixed-shape
page and widget payloads are not filtered.

Serialize payloads with `jsonScriptContent`. Use safe text and attribute
assignment for translated values; do not interpolate them into script bodies
or insert them with `innerHTML`.

### Typed widget IDs

A DOM-free strings module defines each widget's builder and ID union:

```ts
type WidgetStringId = keyof ReturnType<typeof buildWidgetStrings>;
```

The browser imports the type, not the server builder. Give that union to
`CarnapExerciseElement<StringId>` so typechecking rejects IDs the server does
not provide. The default parameter is `never`, making `t()` unavailable until
the subclass declares its string contract.

Never branch on translated text. Use a `data-` attribute or another stable
value instead of comparing `textContent` to an English label.

## Compiler diagnostics

Compiler diagnostics are structured messages so both the Worker and browser
preview can translate them. A `TranslatableMessage` contains a source ID and
parameters, which can themselves be nested translatable messages.

The resolvers in `translator.ts` are:

- `resolveMessage(message)`: English for APIs, logs, and tests.
- `translateMessage(message, i18n)`: translation through a server catalog.
- `resolveMessage(message, stringsResolver(map))`: browser payload lookup.

Author diagnostic IDs are listed in
`src/worker/application/content/diagnostic-strings.ts`.
`CompilerDiagnostic.message` is constrained to that map's keys. Types derive
placeholder names from the ID and require the corresponding parameters.
Add the message to the map when introducing a diagnostic; pass a nested parser
message as data rather than interpolating its English resolution.

### The proof engine's own language

`@aufbau/compiler` owns its diagnostic catalogs. The shared browser compiler
loader in `src/client/proof-compiler.ts` passes the document's `<html lang>`
to `loadCompiler`. One compiler instance serves the document, so its locale
is document-wide rather than per exercise.

An unsupported locale, including `en-XA`, falls back to the engine's English.
Adding an application locale does not add engine translations; check the
upstream package separately.

Application wrappers such as engine-load errors and goal labels still belong
in this repository's catalogs, through `exercise-kit/proof/engine-strings.ts`.

## Tests

The following test files live under `tests/`:

- `i18n-extraction.test.ts`: literal calls use catalog IDs and supported
  forms.
- `i18n-staleness.test.ts`: PO and generated catalogs match current source,
  and checking does not modify them.
- `i18n-pseudo.test.ts`: rendered fixtures use `en-XA` and do not retain
  searchable English catalog IDs.
- `i18n-bundle-guard.test.ts`: the browser import graph and built bundles
  contain no application Lingui runtime or catalogs.
- `i18n-catalogs.test.ts`: locale loading, fallback, keys, memoization, and
  placeholder preservation.
- `i18n-routes.test.ts`: localized error pages and recipient-specific email.
- `locale.test.ts`: both middleware passes, profile choice, cookies, CSRF,
  and LTI locale adoption.
- `exercise-strings.test.ts`: widget maps and hydration preserve IDs and
  placeholders.
- `exercise-review-hydration.test.ts`: review renderers supply translations.
- `ui-strings.test.ts`: browser-filled templates preserve placeholders.
- `editor-preview-strings.test.ts`: rebuilt previews keep their language and
  omit redundant fallback entries.
- `diagnostic-strings.test.ts`: diagnostic coverage, nesting, and localized
  application errors.
- `error-messages.test.ts`: application errors use deferred messages.
- `grade-failure-backfill.test.ts`: stored failure-code migration behavior.

### Coverage limits

The strict pseudolocale test searches for catalog IDs that have no
placeholders and either contain a space or are at least twelve characters
long. It is particularly useful for finding a hard-coded duplicate of a
message translated elsewhere.

It can inspect only text the fixtures render. A new template, error branch,
or widget state needs a fixture in `tests/a11y/fixtures.ts` to be covered.
A passing run is not proof that every catalog message or page was exercised.
The advisory report also looks for other residue and uses a baseline because
proper names, formulas, and authored content may legitimately remain
unchanged.

The bundle guard combines an import-graph walk with scans for runtime markers
and translated catalog text that survive minification. Keep both checks;
searching for an import specifier alone cannot detect a bundled dependency.

Create Lingui instances through `i18nFor`. `setupI18n` expects catalogs keyed
by locale, for example `{ de: catalog }`, rather than a bare catalog. The
wrong shape can return English IDs without throwing.

## Deploying

The development shell sets `NODE_ENV=development`. The current
`wrangler.jsonc` does not override it, so a deploy from that shell can retain
Lingui's runtime message compiler and ICU parser in the Worker.

For a production Worker build, add this Wrangler definition and repeat it
in each named deployment environment, since `define` is not inherited:

```json
{
  "define": {
    "process.env.NODE_ENV": "\"production\""
  }
}
```

This is a configuration change to make before deployment, not a setting
already present in the repository. The standalone container separately sets
`NODE_ENV=production`.

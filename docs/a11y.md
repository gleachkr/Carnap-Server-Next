# Accessibility testing

Carnap targets **WCAG 2.2 AA**. No tool can certify conformance — automated
checks reliably cover only a minority of the success criteria (SCs) — so the
strategy is three tiers: two automated (to catch regressions and inventory the
backlog) and one manual (for everything automation can't see).

| Tier | What | Where | Speed | In the gate? |
|------|------|-------|-------|--------------|
| 1 | axe-core structural rules over server-rendered HTML in jsdom | `bun test` (`tests/a11y/`) | ~10 s | **yes** |
| 1½ | the palette's own arithmetic: token integrity and contrast, both palettes | `bun test` (`tokens.test.ts`, `contrast.test.ts`) | <1 s | **yes** |
| 2 | full axe-core (incl. contrast) in headless Chromium vs a running server | `scripts/a11y-audit.mjs` | ~30 s | no (needs a server) |
| 3 | keyboard / screen-reader / focus / reflow by hand | `docs/a11y-manual.md` | manual | per release |

Tiers 1 and 2 share one engine (axe-core) so rule ids and WCAG tags line up, and
each runs in one of two **modes** against a committed baseline:

- **Gate (ratchet).** Fails only on findings whose fingerprint is *not* in the
  baseline, so new regressions block work while the known backlog is tracked,
  not required to be fixed first.
- **Report (inventory).** Prints the whole current set grouped by rule/SC; with
  `--update` it regenerates the baseline. The baseline file **is** the backlog —
  a shrinking list in a diff is progress; a growing one is a regression a
  reviewer will see.

## Tier 1 — structural gate (always on)

Runs in `bun test` via `tests/a11y/a11y.test.ts`. It renders one representative
sample of every page template (`tests/a11y/fixtures.ts`) plus the standalone
exercise content document, and runs the AA ruleset in jsdom
(`tests/a11y/axe-runner.ts`). jsdom has no layout engine, so contrast,
target-size, and visibility rules are **disabled here** and left to Tier 2.

The runner attaches every `<template shadowrootmode>` as a real shadow root
before auditing, because jsdom's parser ignores declarative shadow DOM and axe
does not look inside a template. Without that step the tier saw only the light
DOM of the six exercise widgets — prompt, slotted labels, action bar — and none
of the chrome that *is* the widget: its group and legend, the option inputs, the
grid of cells. That failure was silent (audit runs, reports the light DOM,
passes), so `a11y.test.ts` asserts the traversal directly against a fault planted
inside a shadow root.

```bash
bun test tests/a11y/a11y.test.ts   # the gate (also runs as part of `bun test`)
bun run a11y:report                # print the full Tier 1 backlog
bun run a11y:baseline              # regenerate tests/a11y/baseline.json
```

Baseline: `tests/a11y/baseline.json`.

## Tier 1½ — the palette, checked as arithmetic

Two tests over `src/worker/web/styles.ts`, both in the default gate, both
instant, and both there because the app has **two palettes** and the second one
fails in ways nobody looking at a light screen can see.

`tokens.test.ts` — every `var(--x)` in `src/` resolves to a token the `:root`
block defines, and every `var(--x, <fallback>)` fallback repeats that token's
light value exactly. The fallbacks are load-bearing (a `cssReset` content
document has no stylesheet of ours, so they are the widgets' only colour), and
a drifted one pins a light hex that renders *inside a dark widget*. On
introduction this found three tokens used but never defined and twenty-six
drifted fallbacks.

`contrast.test.ts` — computes WCAG ratios for the pairings the application
actually draws and asserts them **for every palette the stylesheet defines**,
resolving each `@media` block against the base it inherits from. It reproduces
every ratio quoted below to the second decimal. It does not replace Tier 2:
it checks pairs we know about, where axe checks what a page really renders.

## Tier 2 — browser audit (on demand / pre-release)

Full axe-core in real Chromium, so rendering-dependent SCs are covered:
**colour-contrast**, target-size, the content **iframe**, open **shadow DOM**
(the exercise custom elements), and post-hydration/enhanced widget states. Needs
a dev server and a Chromium binary, so it is not in the default `validate` gate.

```bash
bun run dev                        # in one terminal (serves :8787)
bun run a11y:audit                 # gate: exit 1 on findings not baselined
bun run a11y:audit:dark            # the same, as a reader whose OS is dark
bun run a11y:audit:report          # print the full Tier 2 inventory
node scripts/a11y-audit.mjs --update            # regenerate the browser baseline
node scripts/a11y-audit.mjs --base=… --email=…  # override server / login
node scripts/a11y-audit.mjs /courses/…/assignments/…   # audit extra routes
```

The driver uses Node builtins only (same CDP approach as the `page-shot` skill),
reads `axe.min.js` from `node_modules`, and injects it into every frame. Findings
are normalised — positional `:nth-child` selectors collapse to the offending
component and per-record id/token route segments template to `:id` — so the
baseline (`tests/a11y/baseline.browser.json`) keys on the real issue rather than
on whatever rows the dev database happens to hold.

### `--dark`

`--dark` emulates `prefers-color-scheme: dark`, which is the whole of how the
dark palette is reached — there is no toggle and no cookie — and applies to
every frame, so the content document is audited in dark too. **Run it as well
as the light audit before a release:** colour-contrast is the one rule class
that cannot be checked without rendering, and the second palette is what puts
it most at risk.

Findings are fingerprinted `dark :: …`, so one baseline file holds both
palettes, `--update` merges rather than replaces, and neither run reports the
other's entries as newly passing.

### Borrowed by the i18n work: `--lang` and `--overflow`

This is the only harness in the repo with a real layout engine, so the
translation work reuses it to find copy that only fits in English:

```bash
bun run i18n:overflow    # = --report --overflow --lang=en-XA
```

`--lang=TAG` sends `Accept-Language: TAG` on every request (the header, because
`?lang=` is deliberately not a detection source — see
`src/worker/middleware/locale.ts`). `--overflow` additionally reports text
clipped by its own container, or spilling past the viewport, in the page and in
the content iframe.

The predicate ignores anything that scrolls on purpose — a wide table, a code
block — including elements *inside* such a scroller, since those are meant to
extend beyond the fold. It is advisory and never changes the exit status: the
`en-XA` pseudolocale expands text about 35%, which is harsher than any real
language. See `docs/i18n.md` for the rest of the translation tooling.

## Tier 3 — manual

Automation misses most of AA. `docs/a11y-manual.md` is the per-release checklist
for keyboard operability, screen-reader output, focus order, reflow/zoom, and
dialog behaviour — the SCs that need a human.

## Current backlog

Both baselines are currently **empty**, in both palettes — every issue the
automated tiers have found so far is fixed, and the dark audit's 19 routes came
back clean on its first run. What's fixed (and pruned): the timezone `<select>`
accessible name (`select-name`) and the `.owner-crown` prohibited ARIA attribute
(`aria-prohibited-attr`) in `src/worker/web/courses.tsx`; the green
`.status-badge-ok` badge contrast, the read-only `/profile` input contrast, and
the unselected multiple-choice option labels on the submission-review page in
`src/worker/web/styles.ts` (`--green` darkened to `#1b7048`; the other two moved
to `--ink-muted-strong`); and the Prawitz workspace's `aria-required-children`.

### The two muted inks

In the **light** palette, `--ink-muted` (`#5f7388`) clears 4.5:1 on `--surface`
(4.58:1) and `--paper-top`, and that is where nearly all secondary text sits. It
does **not** clear it on the warmer fills: `--surface-soft` 4.39:1, `--paper`
4.09:1, `--rule-soft` 3.66:1. So there is a second token, `--ink-muted-strong`
(`#4d5f72`) — same hue, dark enough for AA down to `--rule-soft` at 4.9:1 — and
the rule is: **muted text drawn on one of the warm fills uses the strong one.**

Two places do today: the read-only input (on `--rule-soft`) and the
multiple-choice review options (on the submission card's `--surface-soft`). The
second was a live browser finding; the first had been carrying an anonymous
darker hex for the same reason, now named.

Darkening `--ink-muted` itself to `#4d5f72` app-wide was tried and reverted: it
clears AA everywhere, but across ~23 uses it stops reading as secondary text and
starts reading as ordinary ink, which costs the warm-sheet hierarchy more than
the hypothetical failures were worth. If a *new* muted string lands on a warm
fill, reach for `--ink-muted-strong` rather than moving the base token.

**In the dark palette the same two tokens are ordered the other way round** —
`--ink-muted-strong` (`#aca291`) is *lighter* than `--ink-muted` (`#988e7e`),
because contrast against a dark ground runs the other direction. The names say
"more contrast", not "darker", which is why they survive the flip;
`contrast.test.ts` asserts the ordering explicitly, since an inversion there
would be easy to write and almost impossible to spot.

The interesting asymmetry: in dark, `--ink-muted` clears AA on **every** surface
— `--paper` 5.69:1, `--surface-soft` 5.37:1, `--surface` 5.18:1,
`--control-surface` 4.76:1, `--rule-soft` 4.52:1. So the warm-fill rule above is
still true but no longer load-bearing there, and `--ink-muted-strong` (5.79:1 at
its worst) is a hierarchy choice rather than a compliance one.

Two things to watch. `--rule-soft` at 4.52:1 has almost no margin, so a nudge to
either token can break it. And the binding constraint has moved: light's tightest
ground is the warmest fill, dark's is `--control-surface` (`#2a241b`), which is
*raised* off the sheet and therefore the lightest thing text sits on.

`--ink-faint` (`#8797a7`) is decoration only — separators, a disclosure triangle
— at ~2.8:1. Nothing a reader has to read or click may be drawn in it. The
content sheet's ⛶ fullscreen link was, and moved to `--ink-muted`: the glyph is
the entire control, so read as text it wanted 4.5:1 (1.4.3) and read as an icon
it wanted 3:1 (1.4.11) — it cleared neither.

Neither tier had flagged it. axe does look at the element and returns it as
`incomplete`, with `messageKey: "nonBmp"` — *"Element content contains only
non-text characters"*. ⛶ is U+26F6, and axe declines to judge a run of symbol
characters because it cannot tell text from icon; the gate then reports
violations only, so an `incomplete` is silent. Worth remembering for any other
glyph-only control: **the audit cannot see its contrast at all.**

### Known follow-up (not yet flagged by tooling)

- The theory panel's disclosure triangle (`.aufbau-theory-summary::before`,
  `src/worker/exercises/aufbau-proof/theory-panel.ts`) is `--ink-faint` on
  `--surface-soft`: 2.69:1. It is a CSS-border shape, not text, so 1.4.3 does not
  reach it, but it is the open/closed state indicator of a control, which 1.4.11
  asks 3:1 for. The counter-argument is that the panel visibly opening *is* the
  state indication and the triangle only reinforces it — hence "arguable" rather
  than "broken". Left as-is deliberately; if it gets fixed, `--ink-muted` on that
  fill is 4.4:1 and `--ink-muted-strong` is 5.9:1. Under the dark palette the
  same pairing is 3.02:1 and so already clears 1.4.11 — the argument only has to
  be made for light.

Prune the baselines with the `--update` commands as items are fixed.
